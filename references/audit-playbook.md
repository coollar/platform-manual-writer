# 成品实机复查手册

手册**写完 ≠ 写对**。本文件给出"用自建真实案例逐条证伪成品手册"的完整方法。

## 一、为什么必须复查

- **只做"文档内部一致性比对"不算复查。** 读本地文件互相比对，只能证明"两份文档没有自相矛盾"，**证明不了"文档与系统一致"**。曾有一轮只做了文件比对，被明确要求补做上机复核。
- **作者的盲区是系统性的。** 无论人或 AI，都会把"看起来合理"当成"事实"。手册最常见的三类错，全都是"想当然"：
  1. **表格漏列** —— 实机列名与手册写的对不上（如漏了"更新时间"列）
  2. **状态枚举不全** —— 只写了两个状态，实机有三个（漏了"已归档"）
  3. **按钮的适用范围 / 位置写错** —— 如手册说"某图标仅在已发布行末尾"，实测是"操作列最左侧、三种状态都有"
- **复查是唯一能证伪的手段。** 只有到系统上亲手做一个对象、推到那个状态、看到那个结果，才算证据。

## 二、和"探查"的区别

| | 探查（阶段一） | 复查（阶段四） |
|---|---|---|
| 时机 | 写手册**前** | 手册写**完后** |
| 目的 | 建立事实底账，供写作 | 证伪成品的每一个断言 |
| 数据 | 可只读现成数据、看截图 | **必须自建案例**，覆盖所有情况 |
| 范围 | 按写作需求定向 | **穷举式**覆盖所有状态 / 分支 / 边界 |
| 产出 | 写作依据 | PASS/FAIL 核对表 + 偏差修正 |

探查是"拿到素材"，复查是"回头验货"。两者不可互相替代。

## 三、四条核心原则

1. **自建案例，不用现成数据。**
   手上有真实对象可以读，但"能读"不等于"验证到位"。**自己新建**对象、亲手推到目标状态，才能覆盖所有分支——现成数据未必处于你要验证的状态（如"全平台一条草稿任务都没有"时，就无法用现成数据验证草稿行的按钮）。

2. **覆盖所有情况，不只验正常路径。**
   每个状态、每个分支、每个边界、每个异常，都要走到。只验"顺利走通一遍"是最常见的敷衍。

3. **一手证据。**
   每条断言要有实测结果（截图 / DOM dump / 接口返回），不是"我认为应该是"。证据要能复核——出争议时当场对证。

4. **零残留。**
   所有自建对象用完即清，最后按测试前缀**全平台搜一遍**。残留一个测试对象就是一次生产污染。

## 四、复查六步

### 第一步：提断言清单

把手册里**所有可验证的断言**抽出来，逐条编号。一条断言 = 核对表的一行。
（分类见[第五节](#五断言分类清单)）

### 第二步：为每条断言设计案例

对每条断言问一句：**"要观察它，我需要系统处于什么状态？我能不能自己造出这个状态？"**

- **能造** → 自建对象，推到该状态（这是主体）
- **不能造**（如需要第二个账号验证权限互斥、需要历史数据、需要多角色）→ 标注「**无法自建**」，写明原因，**本轮跳过并在报告中列出**，不要蒙混过去

### 第三步：跑脚本，逐条 PASS/FAIL

参考 `scripts/audit_template.js` 写复查脚本。设计要点：

- 复用阶段一的 `state.json`，不重复登录
- 一条断言一个 `check(name, fn)`；`fn` 返回 `true`=通过，返回字符串=失败原因
- 只读断言与写断言走同一套收集，便于统一汇总
- 每条断言顺手截图存档
- 结束打印 PASS / FAIL 清单与总数

### 第四步：处理 FAIL —— 先分清是谁错

FAIL 分两类，**必须先判断再动手**：

| 类型 | 特征 | 处置 |
|---|---|---|
| **手册错** | 实测与手册表述不符（漏列、枚举少、限定写错） | 回**阶段二**改手册 |
| **脚本错** | 选择器没点中、文本被截断、控件不是 `<button>`、表格行序偏移 | **修脚本重跑**，手册不动 |

真实案例中，初跑 45 条断言报 4 个 FAIL，细查后**全是脚本缺陷**（文本截断、列名含空格、"展开"不是 button）——手册本身无误。**如果把脚本的 FAIL 当成手册的错去改，就会把对的改错。**

### 第五步：清理 + 扫残留

- 自建对象全部删除（逐条确认从列表消失）
- 按测试前缀**全平台扫描**，确认零残留
- 有**收敛不了的残留**（如某对象归档后无法删除）→ 在报告里明确列出，不要隐瞒

### 第六步：回改 → 重跑

手册改完 → **重跑阶段三结构校验**（改内容可能影响图号 / 表格数）→ 需要时重跑复查 → 再进阶段五发布。

## 五、断言分类清单

从手册里提断言时，按这几类扫一遍，避免遗漏：

| 类别 | 例 |
|---|---|
| **操作结果** | 点【创建任务】打开抽屉，而非直接建出任务 |
| **状态变化** | 发布后状态由「草稿」变「已发布」 |
| **按钮可用性** | 已发布行有「归档」、草稿行没有 |
| **按钮位置 / 适用范围** | 某图标在操作列**最左侧**、**三种状态都有** |
| **图标按钮 / 悬停提示** | 操作列某处有个**无文字图标**，悬停显示「创建副本」 |
| **按钮穷举完整性** | 手册里写的按钮集合 = 实机该状态的按钮集合（不多不少） |
| **枚举值** | 状态筛选 = 草稿 / 已发布 / 已归档 |
| **必填性** | 任务用途必填、采集设备选填 |
| **二次确认** | 归档有确认框；停用无确认框、点下即生效 |
| **不可逆性** | 归档后回不到已发布 |
| **列表列名** | 表格列 = 模板ID / 名称 / … / 更新时间 |
| **字段只读性** | 采集方案区只读显示，不可改 |
| **默认值** | 任务名称默认取方案名 |
| **提示文案** | 留空提交时的提示语 |

## 六、覆盖矩阵：什么叫"所有情况"

对**每一个对象**，至少覆盖以下维度：

### 1. 状态维度（重灾区）

逐一列出对象的所有状态，验证每个状态的**行操作差异**和**可做/不可做**：

| 对象 | 状态 | 要验的 |
|---|---|---|
| 方案 | 草稿 / 已发布 / 已归档 | 每态的按钮集合、图标有无、可否建任务 |
| 任务 | 草稿 / 已发布 / 已归档 | 同上 |
| 项目 | 开启 / 关闭 / 归档 | 卡片菜单各项的禁用状态 |

> ⚠️ 手册最容易在这里出错：**"仅某状态有"这类限定，必须逐状态实测**。核按钮时先跑 `scripts/inventory_buttons.js` 把实机按钮扫全，再与手册对，见 `references/button-inventory.md`。

### 2. 前后置维度

- 前置不满足时，按钮是**禁用**还是**点了给提示**？
- 只读态下的字段是否真的不可编辑？

### 3. 边界维度

- 必填项**留空**提交 → 提示什么？
- 名称**超长** → 是否截断 / 报错？
- **只读字段**尝试编辑 → 是否被拦截？

### 4. 按钮穷举维度

先按 `references/button-inventory.md` 在实机上**把该状态的按钮全部扫出来**，再与手册逐项对——**这是"不多不少"的核对**：

- 手册写了、实机没有 → 手册虚构或已改版
- 实机有、手册没写 → **漏写**（最常见：无文字图标、禁用按钮、菜单里的项）
- 位置 / 适用范围不符 → 限定条件写错（重灾区）

每个按钮至少 4 条断言：**存在性 + 位置 + 可用态 + 点击结果**。

### 5. 高危维度

- 所有"**有无二次确认**"的断言，实测
- 所有"**是否不可逆**"的断言，实测
- 所有"**点下即生效**"的开关类按钮，实测（在自建对象上）

### 6. 不可验证项

明确列出**无法自建**的断言（需第二账号 / 需历史数据），说明原因，标注为"本轮未覆盖"。

## 七、实战教训

1. **只做文档比对 ≠ 复查。** 必须上机。这是本手册诞生的直接原因。
2. **最容易错的是"限定条件"。** "仅 XX 状态""只在 XX 位置"这类话，写的时候最顺、实测最打脸。
3. **枚举值要以实机下拉为准。** 手册写的状态列表，必须和实机筛选下拉逐项对上。
4. **表格列名要逐列比。** 别凭印象，把实机表格的表头整个 dump 出来对。
5. **分清手册错与脚本错。** 初跑的 FAIL 大概率有一半是脚本自己的问题。
6. **高危操作只在自己造的对象上做。** 复查不能拿真实业务数据冒险。
7. **写不进"无法自建"的，要如实标注**，别用推断把空白填满——那正是复查要消灭的东西。
8. **按钮要"不多不少"地核。** 手册漏写一个无文字图标（如「创建副本」）比写错更隐蔽——读者根本不知道它存在。核按钮时**先在实机上把按钮扫全**（`scripts/inventory_buttons.js`），再与手册对，缺一个都算 FAIL。
