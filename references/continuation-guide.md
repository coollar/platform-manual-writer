手册几乎不会一次写完，而是**一个模块一个模块地往里追加**。本文件给出"给已有手册新增模块章节"的完整方法——它和"从零写"是两件事。

## 一、续写 ≠ 从零写

从零写是"搭骨架"，续写是"往有血肉的身体上加器官"——**加错了会伤到已存在的部分**。

| | 从零写 | 增量续写 |
|---|---|---|
| 结构 | 一次定好 | 已有结构**不可随意动** |
| 头部 | 顺手写 | 散落多处，**必须逐处同步** |
| 图号 | 顺序编 | 新图要么接末尾、要么重排 |
| 风险 | 搭歪了重搭 | 改坏一处 → 全文校验失效 |

**核心原则：只做加法、最小改动。** 新模块尽量插在**结构上说得通、且改动面最小**的位置；不要顺手"优化"已有章节。

---

## 二、续写七步

```
① 定位插入点   —— 读现有 H1/H2 结构，确定新模块往哪插
② 动笔前确认   —— 与用户确认「落位 / 颗粒度 / 简版顺序」再动手
③ 实机探查     —— 按新模块需求只读探查（复用已有登录态）
④ 写作         —— 产出新章节 XML（体例对齐已有章节）
⑤ 头部同步     —— 逐处更新头部散落信息（见第四节）
⑥ 安全落笔     —— 用 scripts/insert_section.py 命中校验后插入
⑦ 校验发布     —— 结构校验 → 复查 → 推送回查
```

**② 为什么不能省**：用户的工作习惯是**先定方向再动笔**。章节落位、颗粒度、简版里的顺序——这三件事方向错了会整体返工。动笔前用一次提问把这三点定下来。

## 三、章节落位怎么定

**问三个问题**：

1. **平台结构上它归哪？** —— 照平台自己的模块划分走，不按个人理解重排。
2. **两版位置是否相同？** —— 详细版按平台结构排；简版可能按"配置类靠前、流程类居中、独立模块靠后"另排。**两版位置可以不同，但各自必须自洽。**
3. **插在中间还是末尾？**
   - 插**末尾**：最省事，图号直接往后接，不动已有编号 → **优先选**
   - 插**中间**：结构上更合理，但**其后所有图号要顺延**，必须重排

> 真实案例：真机回流是平台顶部**独立模块**，且排在讲完数采中心各模块之后，所以直接**追加为末章**——图号往后接，零重排。

**落位一旦确定，简版与详细版分别定位插入锚点**（通常是"最后一章的最后一个 `</p>`"或某个明确的章节边界）。

## 四、头部同步清单（最易漏）

续写时**最容易犯的错**：正文加了、头部忘了改，导致"下半本新版、上半本旧版"。每加一个模块，**逐一核对以下 8 处**：

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `<title>` | 模块名清单加进标题 |
| 2 | 版本互链 callout | 互链文档的**标题**（含模块名清单）+ 字数描述 |
| 3 | 文档信息表 · 手册名称 | 补新模块名 |
| 4 | 文档信息表 · 手册版本 | 版本号 +1，变更说明写清新模块 |
| 5 | 文档信息表 · 适用模块 | 补新模块，及其归属（哪个 Tab 下） |
| 6 | 适用对象表 | 补新角色 + 对应章节号 |
| 7 | 速查表 | 补新模块的高频操作若干行 |
| 8 | 异常表 | 补新模块的常见问题若干行 |

**简版对应**：版本行（`版本：V1.x ｜ 覆盖 …`）、模块说明索引、常见问题表、状态字典、名词速查。

> ⚠️ **标题顺序要自洽**：`<title>` 里的模块顺序、版本行的模块顺序、正文 H1 实际顺序，**三者必须一致**。曾出现标题把某模块提前、与正文顺序不符的情况。

## 五、图号的插入策略

| 策略 | 做法 | 代价 |
|---|---|---|
| **接末尾**（首选） | 新图从 `图 N+1` 开始往后编 | 零重排 |
| **插中间** | 新图占据中间号段，其后**全部顺延** | 跑 `scripts/renumber.py` 重排 |

**判定**：新模块插在最后一章 → 用接末尾；插在中间 → 必须重排，且重排后**重新全文校验**。

**重排后必查**：正文是否引用过图号（"图 N"）。若正文引用过，重排会打断引用；本类手册的惯例是**正文不引用图号**，图号只作索引，因此重排安全。**但每条图号改动后仍要跑一次 `check_doc.py` 确认 1–N 连续。**

## 六、用安全脚本落笔

**绝不直接手改大文件。** 用 `scripts/insert_section.py`：把每个改动点写成 `old → new` 对，**全部命中才写盘，任一失配就不落盘**。

```bash
python scripts/insert_section.py draft.xml --edits edits.json --backup draft_vN_backup.xml
```

`edits.json`：

```json
{
  "edits": [
    { "tag": "title", "old": "…旧标题…", "new": "…新标题…" },
    { "tag": "doc-version", "old": "…V2.4…", "new": "…V2.5…" },
    { "tag": "ch21", "append": "…新章节 XML…" }
  ]
}
```

- `old`/`new`：**精确替换**，`old` 必须恰好命中 1 次（防歧义）
- `append`：追加到文末（幂等，已存在则跳过）
- `optional: true`：允许该点命中 0 次（用于"可能已改过"的点）
- 任一非 optional 点失配 → **整体不写盘**，退出码非 0

**为什么这样设计**：一次续写可能涉及 8–20 个改动点。手工逐个替换，漏一个不会报错；用这个脚本，**漏一个就整体不写**，强制你补齐。

## 七、跨会话接续

手册项目常跨多天。**每完成一个模块，把接续信息写进项目记忆**（如 `.workbuddy/memory/YYYY-MM-DD.md`）：

- **当前版本号**（简版 Vx.y / 详细版 Vx.y）+ 线上 revision
- **已写完的模块清单**，以及**还剩哪些模块**
- **图号区间**（详细版当前最大图号、简版当前最大图号）
- **备份文件名**（本轮的 `xxx_backup.xml`）
- **遗留待办**（未能验证的断言、待用户定的问题）

下次接续时先读这段记忆，避免"忘了写到哪、图号从几开始"。

## 八、实战教训

1. **头部 8 处漏一处，文档就自相矛盾。** 用第四节清单逐项打钩。
2. **标题顺序三处必须一致**（title / 版本行 / 正文 H1）。
3. **能追加就别插中间。** 插中间要重排图号、重跑全文校验，成本高。
4. **别顺手改已有章节。** 续写的目标是加新模块，不是重构——改坏了校验全失效。
5. **落位先确认再动笔。** 章节位置、颗粒度、简版顺序，方向定错全返工。
6. **改动必走安全脚本。** 手工替换漏改不自知；脚本失配立即中止。
7. **改完必跑校验、推送必回查。** 续写改的是文末 + 头部，两处都可能坏。
