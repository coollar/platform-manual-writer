手册的价值一半在内容、一半在**体例统一**。读者靠结构建立预期，体例一乱就"读不懂"。本文件定义双版本的体例规则。

## 一、双版本定位

| | 简版 | 详细版 |
|---|---|---|
| 读者 | 日常操作的人 | 需要查细节 / 对接 / 交付评审的人 |
| 组织 | 一个模块 =「模块说明」+ 若干功能小节 | 全量章节，含数据字典、状态机、路径看板 |
| 图 | 功能小节末尾紧贴截图 | 更多截图 + 流程图 |
| 表格 | 精选（常见问题 / 状态字典 / 名词速查） | 全字段枚举、拦截规则、操作对照表 |
| 关系 | 精简版 | 加详版 |

**两版内容同源、事实必须一致。** 详细版是简版的超集（结构更全），但同一事实的表述**不得互相矛盾**。改一版要同步检查另一版。

## 二、通用写作红线

1. **界面里没写死的，都不能凭推断写。**
   凡描述交互行为，先实机看一眼。宁可写"详见界面"，也不写推断。历史教训：多处"按常识推断"的描述被实机推翻（如"切换分组视图""及规则参数"）。

2. **不写 URL、路由、查询参数。**
   两版一律不出现 `?tab=`、`&stab=`、`/project/...`、`/device/...` 等。页面位置只用界面导航描述：
   - ✅「点项目卡片 →「采标方案」Tab →「采集方案」子 Tab」
   - ❌「访问 /project/142/collect-task?tab=schema」
   - 也不提"复制链接给同事""地址栏"。
   - **例外**：登录地址、两版互相跳转的链接、外部规范文档链接。

3. **不写解释性铺垫。**
   去掉"本节将介绍…""综上所述""值得注意的是"。内容直接进表、进条。

4. **不用 emoji 图标**（✅❌ 等），克制使用加粗。

5. **字数向目标靠。** 简版控制在"正文 ≤ 6 千字 / h1 ≤ 5 / 表格 ≤ 5"量级；详细版保留全部细节。

## 三、简版体例

**一个模块 = 一段「模块说明」+ 若干「功能小节」。**

- **模块说明**：3–5 句话讲清"这个模块管什么、和别的模块什么关系"。作为 `## 模块说明` 二级标题。
- **功能小节**：每节 = **3–4 条编号步骤**，每步一行。
  - `【】` 表示**按钮**（如【新建】【确 定】）
  - `*` 或「必填」标注必填项
  - `**完成：**` 引出**判据**（怎么算这一步做成了）
- **小节末尾紧贴截图**（不隔段落）。
- **结尾两件套**：「常见问题」一张三列表 + 「附录」（状态字典 / 名词速查 / 注意事项）。

**不写**：逐操作速查表、多层路径看板、角色层级表、文档信息表、每章流程图。

### 步骤条目写法示例

```
1. 点右上角【新建】，打开「新建采集任务」抽屉。
2. 填任务名称；采集方案区只读显示，不可改。任务用途、目标条数为必填。
3. 点【确 定】。完成：任务出现在列表，状态为「草稿」。
```

## 四、详细版体例

保留全部细节，面向查阅与评审：

- 文档信息表（版本、更新日期、适用范围）
- 项目背景 / 适用对象 / 阅读与操作约定
- 状态与拦截规则（状态机、状态字典、操作拦截表）
- 全流程概览 + 各模块章节
- 字段枚举（每个字段的类型、必填性、可选值）
- 接口取值说明（如需要）
- 路径看板（三层：页面路径 / 操作路径 / 状态流转）
- 操作对照表（操作 / 入口 / 前置条件 / 结果）
- 异常与停止原则

**章节开头的「本章路径」流程图**：呈现该章的页面跳转与状态流转。**全册统一连续编号**（路径图也是插图，占图号）。

## 五、截图规范

- **一图一义**：一张图讲一件事，不堆叠。
- **红框 + 圆形序号**标注关键区域（用 `scripts/capture_lib.js`）。
- **图注**：`caption="图 N  简短说明"`，说明写"这张图能看到什么"，不写废话。
- **编号全册连续**：图 1–N，无跳号无重号。改动后跑 `scripts/renumber.py`。
- **图文紧贴**：图放在它说明的那段内容之后，不要跨节漂移。
- **归属正确**：图不能落在不相关的小节（曾出现"看板图挂在模块说明末尾"的错位）。

## 六、表格优先原则

**并列信息一律进表。** 长句堆砌是"读不懂"的头号原因。

典型场景：

| 场景 | 表头示例 |
|---|---|
| 状态→可用操作 | 状态 \| 按钮 \| 能做什么 |
| **按钮矩阵（逐状态）** | 状态 \| 「操作」列按钮 \| 能做什么 |
| 必填性说明 | 字段 \| 必填 \| 说明 |
| 枚举值 | 值 \| 含义 |
| 异常处理 | 现象 \| 原因 \| 处理 |

**关键技巧**：表格加一列**「能做什么 / 说明」**，解释"为什么给这些按钮"。只列按钮名，读者还是不知道为什么草稿没有归档。

**按钮表必须来自穷举**：表格里的按钮集合要与实机**不多不少**（见 `references/button-inventory.md`）。**无文字图标按钮要单独成句**——它没有文字，列不进按钮列：

> 「操作」列**最左侧**有一个**不带文字的图标按钮**，鼠标悬停显示「创建副本」，**三种状态都有**。

### 反面 → 正面示例

❌ 长句：
> 行操作随方案状态变化：草稿＝编辑 / 发布 / 删除；已发布＝查看 / 片段标注配置 / 创建任务 / 归档，行末另有图标按钮「创建副本」（无文字，悬停可见）。

✅ 表格：

| 方案状态 | 「操作」列按钮 | 能做什么 |
|---|---|---|
| 草稿 | 编辑 / 发布 / 删除 | 方案还没启用，可继续改；发布后才能用来建任务 |
| 已发布 | 查看 / 片段标注配置 / 创建任务 / 归档 | 内容已锁定不能改，只能查看、配标注、建任务或归档 |

> 已发布行末尾另有一个**不带文字的图标按钮**，鼠标悬停才会显示「创建副本」。

## 七、列表编号规范

**问题**：一条流程中间插截图或段落，就得把有序列表切成多段——**飞书对每段从 1 重新编号**，读者看到"两个 1. 2."以为编号断了。

**解决**：续接块的首项加 `seq="起始号"`：

```xml
<ol>
<li>第一步…</li>
<li>第二步…</li>
</ol>
<img .../>
<ol>
<li seq="3">第三步…</li>   <!-- 接着上一段编号 -->
<li>第四步…</li>
</ol>
```

⚠️ **`seq` 只能写在 `<li>` 上**，写在 `<ol seq="3">` 上无效（服务端报 `Unsupported attribute`）。

**例外**：若两组列表各带引导句（如「运营看板：」/「回流看板：」），说明本来就是两个并列主题，各自从 1 开始是对的，不需要续号。

## 八、用户认可的判断标准

判断手册写得好不好，问一句：**能不能直接拿去评审、提给研发？**

- ✅ 内容进表、进条，可核对、可引用
- ✅ 术语前后一致，界面名与系统一致
- ❌ 解释性铺垫、散文式小节的堆砌
- ❌ 名词解释 / 术语表 / 角色层级表这类凑篇幅的内容

**有参考文档/范例时，严格照抄其结构，不自由发挥。** 形式方向先与用户确认，方向错了会返工。

## 九、可读性三原则

"看不懂"是手册被退回的头号原因。除了[表格优先](#六表格优先原则)，还有三条硬原则——它们针对的是**写作者视角**的毛病：

### 1. 术语用界面原名，不自造黑话

读者看到的是界面，手册必须说界面上的话。

- ❌「**行操作**随方案状态变化」→ ✅「**「操作」列按钮**随方案状态变化」
- ❌ 自造简称（"采标方案区""段配置"）→ ✅ 用界面上的 Tab 名 / 字段名原字

**判据**：手册里的每个名词，读者都能在界面上找到对应。

### 2. 一句一概念，不叠塞

一句话塞进 5 组信息，读者要解方程。

- ❌「草稿＝编辑/发布/删除；已发布＝查看/…，行末另有图标按钮…」——**四组信息 + 一个公式写法**
- ✅ 拆成表格 + 独立成句（见[第六节](#六表格优先原则)）

另：**去掉公式式写法**（`A＝B/C`），改成大白话。

### 3. 每条信息补"能做什么 / 为什么"

只给结论不给理由，读者还是不知道怎么用。

- ❌ 只列按钮名：`草稿：编辑 / 发布 / 删除`
- ✅ 补一列解释：`草稿 | 编辑/发布/删除 | 方案还没启用，可继续改；发布后才能用来建任务`

**"为什么草稿没有归档、已发布没有编辑"——这类因果必须写出来**，否则表格只是把长句换了个形状。

## 十、图表制作

手册的"图"分三类，各有做法：

### 1. 主路径图（全书一张）

呈现**全平台**的模块关系与主流程，放在"写在前面"之后。

- **必须覆盖全部模块**，不能只画主线模块（曾出现"只画了 2 个模块、正文却列了 6 个"的错误）。
- 建议分层：**配置层**（标签 / 系统）→ **主流程**（设备 → 采集 → 数据集）→ **独立模块**（回流）。
- 跨模块依赖用**橙色虚线**标注（如"标签供设备类型与采集任务下拉选用"）。

### 2. 章节路径图（每章开头）

呈现该章的页面跳转与状态流转。

- 全册**统一连续编号**，与插图共用图号（不要"有的带号、有的不带"）。
- 图注形如 `图 N  本章路径：XX（流程示意）`。

### 3. 原生画板（whiteboard）

需要**可编辑**时用原生画板，比贴图片更好：

```xml
<whiteboard type="svg" path="@./main_path.svg"/>
```

**制作方法**：
1. 手写 SVG（定好 `viewBox`，配色跟主题；圆角矩形节点 + 箭头连线）。
2. 渲染成 PNG 预览（Playwright）：
   ```js
   await page.setContent(`<body style="margin:0;background:#fff">${svg}</body>`);
   await page.setViewportSize({ width: 1360, height: 960 });
   await page.screenshot({ path: 'preview.png', fullPage: true });
   ```
3. 图片方式用 `<img>`，画板方式用 `<whiteboard>`。

> ⚠️ 画板导出预览返回 **.jpg**，输出扩展名要写 `.jpg`。改动图后记得重跑图号校验。
